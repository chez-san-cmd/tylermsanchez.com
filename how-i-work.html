How I work

An assistant that runs in the background is only as trustworthy as the rules it runs under. Here are the rules, then the system that enforces them, then the tools.

Principles

  1. It never sends anything to another person. Drafts stay drafts until I send them.
  2. It never closes my decisions for me. It recommends; I mark done, decline, approve.
  3. It never spends money. It can comparison-shop and pressure-test a purchase. The card stays with me.
  4. It writes down what it learned. Every project has a book: brief, decisions, open questions, session log. The delta between what it drafts and what I send is how it learns my voice.
  5. It brings me decisions, not updates. Recommendation first, evidence underneath, prep already done.

The system

Me (decides, sends, buys) Scheduled Claude run Notion, the system of record Outside service

The loop

Everything runs on one loop. Scheduled runs read the outside world and the Notion record, do the work an agent is allowed to do, and leave decisions in an attention queue. I read the queue from one page, answer in a line, and that answer starts the next run. Nothing leaves the system to another person unless I send it myself.

Project Books: how it remembers

Every project, from a renovation to a job search to a dinner planner, gets one Notion page with the same four parts. A run reads the book before it does anything and appends a session log line when it is done. That is the whole memory model: no hidden state, and I can read the book instead of the transcript.

Job Radar: fetch, score against a written point of view, bring only the decisions

Two jobs a day. GitHub Actions fetches every PM posting from about twenty company boards and commits the day's new ones. A Claude run then scores each posting against a rubric I wrote about what I actually want (latitude to make bets first, level second, problem space third), writes the ones worth a look to a Notion table with a one-line "why", and sends only 4s and 5s to the attention queue. My Interested / Not for me calls and notes feed the next revision of the rubric.

Concert presales: taste, listings, and the presale email

The point is to know about a show during the presale, before general on-sale and the resale markup. Three inputs: what I actually listen to on Spotify, who is coming to Denver, and the venue and promoter newsletters I route straight to the archive in Gmail. A run matches them, keeps a tiered list of artists, and writes the presale window and code to a table. Tier 1 artists show on the Command Center with the code; Tier 2 is a weekly digest for discovery. I buy.

The learning loop: the delta between the draft and what I sent

The agent never sends mail. It writes a draft in my voice and leaves it in Gmail; I edit and send. On the next run it compares what it drafted to what actually went out, and folds the difference into a writing-style file that every future draft reads. The same shape runs everywhere: Job Radar notes revise the rubric, project books carry decisions forward, and the Command Center queue records which recommendations I took.

Tools

  • Claude (Claude Code and its scheduled tasks) does the reading, drafting, scoring and filing. Every run starts from a written brief and ends with a log line.
  • Notion is the system of record: the attention queue, one Project Book per project, and the radar tables. If it isn't in Notion, the agent doesn't know it.
  • GitHub Actions runs the deterministic parts on a schedule, like the daily job fetch, and keeps the data as plain JSON in a repo.
  • Gmail, Google Calendar and Drive are read through connectors. Drafts are written to Gmail; nothing is sent from there by an agent.
  • Spotify supplies taste for the concert radar; venue newsletters supply the presale windows.
  • A single HTML page is the Command Center: no framework, reads Notion live, and has been changed about a hundred times.
