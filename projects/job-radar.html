Job Radar

Every morning a script pulls every product-management posting from 23 companies I'd consider working for, and a Claude run scores each one against a rubric I wrote about what I actually want. I see only the ones worth a look.

What happened → what I changed

What happened. The first rubric described the jobs I'd like. The first sweep read 75 open roles and flagged 8 as Strong, and when I read those eight, several were strong on paper and wrong for me: big shared surfaces where the PM is a traffic cop, titles that sounded senior but owned no strategy.

What I changed. The same day I rewrote the rubric around what I was actually optimizing for, in weight order: latitude to originate product bets, then level, then problem space, plus the uncomfortable constraints (pay floor, hours, how AI-native the team is). Re-scoring the same roles gave 5 Strong, 14 Maybe, 52 Pass, and the Strong list was one I'd act on. The model was never the problem; my clarity was.

What it does

Two jobs a day. Around 5am Denver time a GitHub Action fetches the PM postings from each company's own job board and commits the day's new ones to a repo. At 6:52am a scheduled Claude task reads each new posting in full, scores it 1 to 5 against the rubric, and writes anything scoring 3 or above to a Notion table with a one-line "why" a recruiter could read. Anything that scores a 4 or 5 also lands in my attention queue the same day; everything else waits for a Sunday review item that lists the week.

I mark each row Interested or Not for me, sometimes with a note. The notes get folded back into the rubric, so the scoring drifts toward my actual judgment rather than my first description of it. It has been running since October 5 and reads about a hundred postings a week so I don't have to.

Why I built it

I'm between roles and in no hurry, and the plan assumes the main levers for the next job are people and stories, not applications. But a rare ideal role can appear at any time, and I didn't want to spend an hour a week scanning career pages to catch it. The Radar is a passive net: it watches, I decide. It also turned out to be the cleanest small example of the shape I think most useful agents will take: fetch on a schedule, score against a written point of view, bring only the decisions to a human.

How it's built

  • Fetch. A private repo with one adapter per job-board platform: Greenhouse, Lever, Ashby, Rippling, Workday (Zillow), Eightfold (Netflix), and a scraper for Shopify, which publishes no feed. A GitHub Action runs the fetch daily and commits new postings as plain JSON, so the history is a git log. Why GitHub Actions: scheduled Claude runs can't open arbitrary websites without a per-URL approval nobody is there to give. Splitting deterministic fetching from judgment-heavy scoring solved that and made each half easier to test.
  • Score. A Claude scheduled task reads the day's file and RUBRIC.md. The rubric scores first on latitude to originate product bets, then level, then problem space. Later rules came straight from my notes on real postings: AI-native teams weigh heavily, "traffic cop" seats on shared surfaces cap at 3, fixed in-office days outside Denver cap at 3 but are still shown, and location is a flag rather than a filter. Director and head-of-product titles are scored on strategy ownership instead of being passed on title.
  • Store and show. One Notion database: role, company, fit, score, why, status, my notes, level signal, location, link. A saved view feeds a tile on my Assistant Dashboard map and the Sunday review. Everything reads through saved views because Notion's row-query API has a workspace quota and views don't.
  • Learn. Daily runs also read the Maybe rows and my notes. A full re-score in the first week moved a few roles between Strong and Maybe; it checks that the rubric is applied consistently, not that nothing was missed. Checking the passes against my own judgment is a standing item in the Sunday review, and the sample so far is small.

A public repo with the fetch adapters, the rubric template and the scoring evals goes up on GitHub in mid-November, at github.com/chez-san-cmd/job-radar. The README there will carry the implementation details this page leaves out.

What I learned

Writing the rubric was writing the job search. Deciding how to weigh latitude against level, or whether in-office days in another city are a flag or a filter, forced decisions I'd been carrying around as vague preferences. The rubric file is now the clearest statement I have of what I want next, and it gets revised every time I disagree with a score.

Flags beat filters. My first instinct was to filter out roles in other cities. Keeping them visible as a capped score instead leaves room for the conversation I actually want to have, which is whether the role could be rescoped to remote.

Some boards don't move. Shopify's careers page is one evergreen posting, so the Radar will almost never show anything new there. For companies like that, a person on the inside matters more than a feed.

Scheduling is the flaky part. GitHub's cron has run hours late, so scoring has sometimes run before the day's fetch landed and picked the roles up a day later. The fix is to start scoring when the fetch finishes instead of at a fixed time; it's proposed, not built yet, and it's the kind of plumbing that takes more of the week than any prompt.
